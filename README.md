# RideFlow

RideFlow is a production-minded ride-sharing platform built as a modular monolith. Its purpose is to explore backend engineering, geospatial data, concurrency, real-time communication, event-driven architecture, and operational reliability without prematurely splitting the system into microservices.

This repository currently contains **Phase 4: Ride Lifecycle**. Riders can estimate and request rides, and drivers can accept and complete them through an enforced state machine. Automated matching is intentionally deferred to Phase 5.

## Architecture

```mermaid
flowchart LR
    Browser[React web client] -->|HTTP / WebSocket later| API[FastAPI modular monolith]
    API -->|async SQLAlchemy| DB[(PostgreSQL + PostGIS)]
```

The browser, API, and database are separate runtime containers. The backend is one deployable application with `auth`, `users`, `drivers`, and `rides` owning their rules behind internal boundaries. Matching and payment domains follow in later phases.

See [docs/architecture.md](docs/architecture.md) for the detailed shape and [docs/decisions](docs/decisions) for architectural decisions.

## Technology stack

- Backend: Python 3.12, FastAPI, Pydantic Settings, SQLAlchemy 2 (async), GeoAlchemy2, Alembic
- Database: PostgreSQL 16 with PostGIS 3.4
- Frontend: React 19, TypeScript, Vite, Ant Design, React Router, TanStack Query, Zustand
- Tooling: Docker Compose, Pytest, Ruff, mypy, ESLint, Vitest, GitHub Actions

Authentication uses Argon2 password hashes, short-lived JWT access tokens, and rotating opaque refresh tokens. Redis, Kafka, WebSockets, Prometheus, Grafana, and OpenTelemetry are deliberately deferred until the phases that need them.

Driver locations use PostGIS `geography(Point, 4326)` and a GiST index. PostgreSQL remains authoritative; Redis-backed live location and matching are deferred until matching has concrete atomic-reservation requirements.

Ride estimates use PostGIS straight-line distance and database-backed `Decimal` pricing rules. Ride acceptance locks the ride and driver rows, while partial unique indexes independently prevent concurrent active rides for one rider or driver.

## Quick start

Requirements: Docker with Compose support.

```bash
cp .env.example .env
docker compose up --build
```

The backend runs migrations before it starts. Open:

- Web client: <http://localhost:5173>
- OpenAPI UI: <http://localhost:8000/docs>
- Liveness: <http://localhost:8000/health>
- Readiness: <http://localhost:8000/ready>
- Register: <http://localhost:5173/register>
- Sign in: <http://localhost:5173/login>
- Driver workspace: <http://localhost:5173/driver> (requires a `DRIVER` account)
- Rider workspace: <http://localhost:5173/rider> (requires a `RIDER` account)

Stop the stack with `docker compose down`. Add `--volumes` only when you intentionally want to remove local database data.

## Environment configuration

Configuration uses `RIDEFLOW_`-prefixed environment variables. `.env.example` documents all current values. Local defaults are development-only; use externally managed secrets and a strong database password outside local development.

`RIDEFLOW_CORS_ORIGINS` is a JSON list, for example:

```text
RIDEFLOW_CORS_ORIGINS=["https://app.example.com"]
```

## Database migrations

Run migrations against the Compose database:

```bash
docker compose run --rm backend alembic upgrade head
```

Create a revision after adding models:

```bash
docker compose run --rm backend alembic revision --autogenerate -m "describe change"
```

Review autogenerated migrations before applying them. The migrations currently cover PostGIS, authentication, drivers/vehicles, configurable pricing, and the ride lifecycle.

## Verification

Run every check in containers:

```bash
make verify
```

Or run suites independently with `make backend-test`, `make backend-check`, `make frontend-test`, and `make frontend-check`.

## API and realtime documentation

FastAPI generates OpenAPI documentation at `/docs` and `/openapi.json`. The hand-maintained API contract and health semantics live in [docs/api.md](docs/api.md).

WebSockets and Kafka are not present yet. Their intended boundaries and adoption criteria are recorded in [docs/architecture.md](docs/architecture.md) and [docs/events.md](docs/events.md); concrete schemas will be added alongside their implementations.

## Roadmap

1. **Foundation (complete):** monorepo, FastAPI, React, PostGIS, migrations, containers, health checks
2. **Authentication (complete):** users, roles, Argon2, JWT access tokens, rotating refresh tokens, profiles
3. **Drivers and vehicles (complete):** profile verification, availability, vehicles, PostGIS location
4. **Ride lifecycle (complete):** state machine, database pricing, estimates, ride operations, history
5. **Matching (next):** proximity offers, rejection/timeouts, reservation, Redis concurrency protection
6. Real-time tracking: WebSockets and location streaming
7. Payments and ratings: provider abstraction and idempotency
8. Kafka events
9. Reliability patterns and transactional outbox
10. Observability
11. Load and failure testing
12. Evidence-driven service extraction, if warranted
